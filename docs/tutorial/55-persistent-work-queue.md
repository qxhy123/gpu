# Chapter 55 — Queue-Driven Persistent Processing

## Dynamic Queue Growth

Chapter 54 showed the simplest persistent kernel pattern: push all items, stop the queue, then start the kernel. In a real workload the work items often arrive in bursts or are generated by a producer running concurrently with the consumer kernel.

The `persistent_work_queue` example extends the pattern to model a scenario where the queue is loaded in batches before being stopped. The key insight is that `WorkQueue.stop()` can be called at any point after all items have been pushed — the persistent kernel will drain whatever is in the queue at start time.

```python
from gpusim.persistent.queue import WorkQueue

queue = WorkQueue()

# Batch 1: push 2 items
for i in range(2):
    queue.push({"OUT": np.zeros(32, dtype=np.uint32)})

# Batch 2: push 2 more
for i in range(2):
    queue.push({"OUT": np.zeros(32, dtype=np.uint32)})

# Done filling — signal kernel to drain and exit
queue.stop()
```

The `WorkQueue` API enforces two invariants:

- Items pushed before `stop()` are always visible to the persistent kernel.
- Any `push()` after `stop()` raises `RuntimeError("queue stopped; cannot push")`.

## The persistent_work_queue Demo

```python
import numpy as np, pathlib
from gpusim.persistent.queue import WorkQueue
from gpusim.persistent.kernel import PersistentKernel
from gpusim.config.loader import load_default

cfg = load_default()
ptx = pathlib.Path("examples/persistent_work_queue/kernel.ptx").read_text()

queue = WorkQueue()
out_bufs = []

# Push 4 items in two waves, then stop
for _ in range(2):
    ob = np.zeros(32, dtype=np.uint32)
    out_bufs.append(ob)
    queue.push({"OUT": ob})

for _ in range(2):
    ob = np.zeros(32, dtype=np.uint32)
    out_bufs.append(ob)
    queue.push({"OUT": ob})

queue.stop()

pk = PersistentKernel(ptx_src=ptx, grid=(1,1,1), block=(32,1,1),
                      params_template={}, work_queue=queue,
                      kernel_name="server")
results = pk.start(cfg)

print(f"Processed {len(results)} items")   # 4
for ob in out_bufs:
    assert ob.sum() == 32   # each of 32 threads wrote 1
```

Run it:

```bash
python examples/persistent_work_queue/run.py
```

The kernel is identical to Chapter 54's write-1 kernel. The difference is in the queue loading strategy — two push loops instead of one — which models a multi-producer or batch-streaming scenario.

## 看模拟器

**用 is_empty() 验证 pop 顺序：**

`WorkQueue` exposes `is_empty()` and `is_stopped()` for introspection at any point:

```python
queue = WorkQueue()
assert queue.is_empty()          # True — nothing pushed yet
assert not queue.is_stopped()   # False — not stopped yet

queue.push({"OUT": np.zeros(32, dtype=np.uint32)})
assert not queue.is_empty()    # False — one item in queue

queue.pop()
assert queue.is_empty()        # True — drained

queue.stop()
assert queue.is_stopped()      # True
assert queue.is_empty()        # True — empty + stopped
```

The FIFO order guarantee means the first item pushed is the first item the kernel processes. Verify order tracking with a side-channel list:

```python
order = []
queue = WorkQueue()
for i in range(5):
    queue.push({"seq": i, "OUT": np.zeros(32, dtype=np.uint32)})
queue.stop()

# Drain manually without launching kernel (for inspection)
while not queue.is_empty():
    item = queue.pop()
    order.append(item["seq"])

assert order == [0, 1, 2, 3, 4]   # FIFO
```

## 改一改

**用 params_template 注入共享参数：**

`PersistentKernel.params_template` provides a base dict that every work item inherits. Per-item dicts override individual keys. Use this to inject a shared configuration while varying per-item outputs:

```python
import numpy as np

# Shared scale factor (imagine a calibration constant)
SHARED = {"SCALE": np.uint32(2)}

queue = WorkQueue()
out_bufs = []
for _ in range(4):
    ob = np.zeros(32, dtype=np.uint32)
    out_bufs.append(ob)
    queue.push({"OUT": ob})   # SCALE comes from params_template
queue.stop()

pk = PersistentKernel(
    ptx_src=ptx,
    grid=(1,1,1), block=(32,1,1),
    params_template=SHARED,   # merged into every item's params
    work_queue=queue,
    kernel_name="scaled_server",
)
results = pk.start(cfg)
```

Inside `PersistentKernel.start`, the merge is:

```python
params = {**self.params_template, **item}   # item keys override template keys
```

This means per-item params take precedence. If both `params_template` and the work item supply `OUT`, the item's `OUT` wins — the template's `OUT` is ignored. Use this to share expensive-to-copy constants (config structs, lookup tables) across all work items without duplicating them in every queue entry.

## 真机对照

The queue-driven pattern maps directly to the producer-consumer model common in GPU inference servers (TensorRT, Triton Inference Server):

| Aspect | `gpusim` | Production inference server |
|---|---|---|
| **Queue storage** | Python `deque` (host RAM) | Lock-free ring buffer in pinned host memory or device memory |
| **Producer** | Host Python loop pushing dicts | CPU thread or network receiver pushing serialized requests |
| **Consumer** | `PersistentKernel.start()` polling `pop()` | Persistent CUDA kernel polling device-side queue head |
| **Stop signal** | `queue.stop()` → Python boolean | Sentinel batch or atomic shutdown flag polled every N iterations |
| **Queue depth** | Unlimited (Python list) | Fixed ring size (e.g. 256 entries); backpressure via blocking push |

On NVIDIA Triton Inference Server, the equivalent persistent kernel pattern uses `cudaStreamSynchronize` between batches (similar to gpusim's per-item `synchronize()` call) for dynamic batching, while the "in-flight batching" variant uses device-side queues to avoid any host synchronization between items.

The `persistent_work_queue` example demonstrates that the gpusim `WorkQueue` correctly models:
1. FIFO ordering — items are processed in push order.
2. Stop semantics — kernel exits cleanly when queue is empty and stopped.
3. Push-after-stop guard — raises `RuntimeError` if the producer mistakenly continues pushing.

Chapter 56 introduces dynamic parallelism: instead of the host triggering child kernels, the parent kernel itself schedules them via `device_launch`.
